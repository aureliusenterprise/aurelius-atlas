Increment 8.2 — lineage-model API¶

Field Value
Status accepted
Author Aurelius Atlas maintainers
Date 2026-10-23
ADRs 055 (auxiliary APIs are a named data surface), 051 (increments), 049 (traceability), 052 (parity cites the reference; here the reference is Aurelius source)
Design log DD-197 (foundation), DD-199 (test env), DD-200 (proxy app: injectable upstream, canned-file fixture Atlas), DV-69 (stubbed data path)

Objective¶

Port the legacy Aurelius m4i-lineage-model service — the lineage-graph API the webapp's lineage screen calls — to a FastAPI app: apps/aurelius-atlas-lineage-model.

GET / takes guid (required), depth (default 3) and direction (default BOTH), fetches the entity's lineage from an Atlas metadata API (GET {atlas_base_url}/v2/lineage/{guid}), flattens the lineage relations into the 12-column archimate rows, and POSTs them with the fixed lineage rules to data2model /extract (8.1), returning that response body verbatim — the {model, metadata} document the lineage screen consumes. The chain is webapp → lineage_model → data2model /extract.

Per DV-69 the data path is stubbed until the server's lineage feed (5.1): the Atlas base URL is a setting, no increment blocks on 5.1, and the tests use canned lineage fixtures. The caller's bearer token is forwarded to both upstream calls — the legacy's token-passing design (the caller is the browser's own token; 8.1 records why that makes aurelius the audience).

The legacy is a Flask app on m4i-atlas-core (get_lineage_by_guid, LineageInfo dataclasses, requests.post to data2model). The port follows DD-198: pydantic models parse the upstream lineage at the boundary, rows are plain dicts, and the HTTP client is injectable for tests (DD-200).

Scope¶

In scope: the app (settings, app factory, GET /, liveness), the lineage models and flattening, the fixed rules document, unit tests, a parity scenario, container and e2e (Keycloak-protected; the real data2model container; a canned-file fixture Atlas).

Out of scope: the Atlas lineage feed itself (5.1 — the setting points at it), the webapp lineage screen (7.x track), the legacy aiocache @cached() on the fetch (a dev convenience; the screen refetches on navigation — no cache), the m4i-atlas-core library (only the lineage fetch is ported, as a local httpx call).

Contracts and Rules¶

The reference for every rule is the Aurelius source (ADR 055 R4): backend/m4i-lineage-model/m4i_lineage_model/lineage_model.py (lineage_model, fmt_lineage_relation, the rules dict, process_types), libs/m4i-atlas-core/m4i_atlas_core/api/atlas/get_lineage_by_guid.py (path, params), .../entities/atlas/core/lineage_info/LineageInfo.py (camelCase JSON shape), and the webapp caller apps/atlas/src/app/search/details/components/lineage-model/lineage-model.service.ts.

Upstream lineage shape¶

The fetch consumes Atlas's v2/lineage/{guid} camelCase JSON — {guidEntityMap: {guid: {guid, typeName, displayText, …}}, relations: [{fromEntityId, relationshipId, toEntityId}], …} — parsed as pydantic models with extra fields ignored (the legacy's dataclasses_json shape); only the fields the flattening reads are declared (DD-198).

Data contracts¶

  • GET /?guid=&depth=&direction= → 200 {model, metadata} / 204 / 400/401/502 with {"errorCode", "errorMessage"} (LM-01..LM-08).
  • GET /liveness → 204 (LM-09).
  • aurelius_atlas_lineage_model.lineage: LineageInfo, EntityHeaderLite, LineageRelation (pydantic), PROCESS_TYPES, LINEAGE_RULES (the fixed document), flatten_relations(info) -> list[dict].
  • create_app(settings, auth=None, http=None) — http is the upstream httpx.Client (injectable for tests, DD-200); production builds one with a timeout, TLS CA from the auth settings.
  • Settings (env prefix AURELIUS_ATLAS_LINEAGE_MODEL_): host, port (21002), log_level, tls_cert_file/tls_key_file, auth_server_url, auth_realm, auth_audience, auth_ca_file, atlas_base_url, data2model_url, otel_token_url, otel_client_id (otel-lineage-model), otel_client_secret, otel_endpoint, otel_ca_file.

Deviations (recorded in deviations.md)¶

  • DV-72: an invalid depth/direction is 400, not the legacy's Flask ValueError → 500 (LM-07).
  • DV-73: a missing guid is 400, not the legacy's fetch of the literal guid None (→ upstream 404 → 204) (LM-07).
  • DV-80: upstream failures beyond the lineage 404/400 (5xx, dangling guid, failing /extract) are 502 with the Atlas error body, not uncaught exceptions → Flask 500 (LM-07).
  • DV-74: the endpoint fully verifies the bearer token for its audience (AUX-05, DD-197), not the legacy's transparent=True pass-through; browser tokens (azp aurelius) pass both.
  • DV-78: the guid is a UUID on every typed surface (route, client models, LineageInfo), not the legacy's opaque string — a non-UUID guid is the 400 of DV-73 before any upstream call (LM-01, LM-07, DD-213).

Test list¶

  • Unit: apps/aurelius-atlas-lineage-model/tests/test__lineage.py (LM-02..LM-07, the flattening, rules, forwarding, upstream statuses on a mock transport), test__aurelius_atlas_lineage_model_app.py (LM-01/08/09 wiring on the fake issuer), test__aurelius_atlas_lineage_model_settings.py (LM-10), test__…___main__.py.
  • Scenario (parity, read from Aurelius source): scenarios/lineage/graph.scenario.yaml — the caller's fixed rules over the 8.1 scenario's two-relation lineage; the canned /extract answer is the 8.1-verified model document, so the expected body is full equality (no volatile — DV-68 is inside the canned answer).
  • E2E: e2e/ — real container, Keycloak-minted token, the real data2model container, and a canned-file fixture Atlas (dhi.io Python http.server, DD-200); 401 anonymous, 200 chain, 204 unknown guid.

Acceptance criteria¶

  • Every rule id names a test (ADR 049 — aurelius-atlas-trace check green).
  • The forwarded-token chain works end to end (browser token, audience aurelius).
  • Ruff, pyright, prettier, commit checks; nx test/nx e2e pass.
