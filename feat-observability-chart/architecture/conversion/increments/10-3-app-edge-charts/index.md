# 10.3 App and edge charts

- **Status:** in review
- **Pull request:** \#159
- **Records:** ADR 057, DD-238, DD-242, DD-243, DD-251, DD-256, DD-259, DD-261..264

## Scope

The five stateless app charts (`atlas-server`, `atlas-webapp`, `atlas-data2model`, `atlas-lineage-model`, `atlas-validate-entity`) gain their workload wiring, and the umbrella gains the edge: the Gateway, one HTTPRoute per browser host, and the browser-host certificates (DD-242's shape, never yet rendered). This closes DD-251 in full — the aux charts' dead CA mount and lineage-model's unrendered upstream URLs were both assigned here — and DD-253's suite grows one file per chart. The observability stack is split out to 10.3b (its own increment, own PR); 10.3's hand check therefore runs the apps with telemetry pointed at nothing, exactly as 10.2's rendered with `createIssuer` until the chain needed it.

This increment delivers:

- `apps/aurelius-atlas-server/helm` — Deployment + Service, the `AURELIUS_ATLAS_SERVER_` settings joins (store service, issuer token URL, the generated `-elasticsearch`/`-otel-clients` Secrets), a `Certificate` for the service name nginx verifies, HTTPS probes on the admin endpoints (SRV-06: the server speaks TLS, so the probes cannot be HTTP — DD-260's lesson applied before the crash, not after).
- `apps/aurelius-atlas-webapp/helm` — Deployment + Service (plaintext 8080; the Gateway terminates TLS, DD-242), the two ConfigMaps the deployment needs: the nginx config as a byte-copy chart asset of `nginx.conf.template` resolved **at pod start** (init container, `sh` + `sed` — the image has neither `envsubst` nor Helm-time substitution, DD-262), and `/config.json` from values.
- Aux chart completion (all three, DD-251): each gets its own `Certificate` (service-name SANs) and a real `ca.crt` in the mounted TLS volume (cert-manager already puts `ca.crt` in the issued Secret — the dead `tls.caConfigMap`/`tls.caPath` values become honest or go away); lineage-model renders `atlas_base_url`/`data2model_url` from the sibling Services it co-deploys with.
- `helm/` (umbrella) — the `Gateway` (listeners: the atlas host, the keycloak host, the dashboard and grafana hosts when enabled), one `HTTPRoute` per host, the browser-host `Certificate` for the atlas/dashboard/grafana names (the keycloak listener reuses the Keycloak chart's Secret), the `BackendTLSPolicy` resources for the TLS backends (server, keycloak, aux when routed), CA-pinned to the DD-259 chain root, and the generated `-collector-legacy` Secret (the webapp's nginx ingest bearer is its first consumer).
- `tests/` — chart-contract files for all five apps + the edge additions to `test__charts_umbrella.py`.

This increment does not deliver: the observability workloads and the apps' telemetry turning-on (10.3b), the remaining secrets blocks and chart publish polish (10.4), scripted minikube install + smoke (10.5).

## Rules

| Id | Rule |
| --- | --- |
| CHT-20 | The server runs as a Deployment with a ClusterIP Service on its settings port (values `port`, default 21000); liveness/readiness are HTTPS probes on `/api/atlas/admin/liveness` / `/readiness` (the SRV-06 server serves TLS; an HTTP probe would DD-260). `replicaCount` defaults to 1. |
| CHT-21 | The server's settings render as joins, never literals: `ELASTICSEARCH_HOSTS` from the store Service name, `ELASTICSEARCH_PASSWORD` from `<release>-elasticsearch`, `OTEL_TOKEN_URL` from the issuer URL, `OTEL_CLIENT_SECRET` from `<release>-otel-clients`, TLS/CA files from its own Certificate's Secret paths; the image's declared uid (nonroot) with `fsGroup` (DD-257); `FORWARDED_ALLOW_IPS` from values (default loopback — DD-261). |
| CHT-22 | The server's `Certificate` SANs are its Service name and FQDN forms (the name nginx pins with `proxy_ssl_name`); `replicas`/probes/resources are values; no password value renders anywhere. |
| CHT-23 | The webapp runs as a Deployment + Service on 8080 plaintext (TLS terminates at the Gateway, DD-242); HTTP probes; the image's nginx uid with `fsGroup` only where a writable volume needs it (cache/run dirs as emptyDir). |
| CHT-24 | The nginx config is a chart *asset*: `helm/files/nginx.conf.template`, a byte-copy of the app's `nginx.conf.template` (drift-guarded by a byte-compare test, the DD-256 pattern), shipped as a ConfigMap; a `resolve-nginx-config` init container (the same image, `sh` + `sed`) substitutes the `${AURELIUS_ATLAS_WEBAPP_*}` placeholders from the container's environment into an emptyDir mounted over `/etc/nginx/conf.d` (DD-262 — Helm never sees `${AURELIUS_ATLAS_WEBAPP_OTEL_INGEST_TOKEN}`; rendering it in the ConfigMap would re-draw the umbrella's generated value, DD-256's race with a different secret). |
| CHT-25 | The webapp's environment carries the ten template placeholders computed by the chart: API upstream `https://<server-svc>:<server-port>`, OTEL upstream `https://<collector-svc>:4318` (the browser leg, per the e2e reference — the SPA pushes OTLP/HTTP with its Keycloak JWT through `/otel/`) and `OTLP_ENDPOINT = https://<collector-svc>:4320` (the legacy gRPC leg, nginx's own edge-span exporter, DD-239; 10.3b owns the collector — the values are joins and may point at nothing until then, nginx resolves lazily by design), the kube-dns resolver (values `global.dnsResolver`, default cluster DNS Service), Keycloak origins from the issuer host, the CA path from the mounted trust-root Secret (the webapp is a TLS client only — it presents nothing; its listener is plaintext behind the Gateway), and `OTEL_INGEST_TOKEN` from `<release>-collector-legacy` (key `token`). |
| CHT-26 | `/config.json` is a ConfigMap rendered from values (`apiBaseUrl`, `keycloak` {url from the issuer}, `otelExporterUrl`), mounted at `/usr/share/nginx/html/config.json`; the SPA's `initialize()` fetch (fails loudly) is the contract it must satisfy. |
| CHT-27 | Each aux Deployment gets a `Certificate` (its Service-name SANs) and mounts its Secret whole at `tls.mountPath` — `tls.crt`, `tls.key`, and `ca.crt` all present (DD-251: the `AUTH_CA_FILE`/`OTEL_CA_FILE` defaults point at `ca.crt` inside that mount; the dead `caConfigMap` value is retired). |
| CHT-28 | lineage-model renders `ATLAS_BASE_URL=https://<server-svc>:<port>/` and `DATA2MODEL_URL=https://<data2model-svc>:<port>/` from the co-deployed siblings (DD-251's second finding — required settings, no defaults; the hand check boots it with no out-of-band values); the auth audience defaults per app to its `settings.py` default (`aurelius-atlas-lineage-model` et al.) and is a values knob — the dev `aurelius` audience stays the dev deployment's values choice, not the chart's (DV-74/DV-75 name the split). |
| CHT-29 | The umbrella renders one `Gateway` (class `global.gateway.className`, namespace the release's) with a TLS listener per enabled browser host: `atlas.<domain>` (Secret `<release>-edge-tls`, an umbrella `Certificate` whose SANs are the umbrella-owned browser hosts — atlas + enabled dashboard/grafana hosts), `keycloak.<domain>` (reuses the Keycloak chart's `<release>-keycloak-tls` Secret per the name contract), and dashboard/grafana listeners only when their host blocks are enabled. No GatewayClass is ever rendered (prerequisite, runbook). |
| CHT-30 | One `HTTPRoute` per listener, hostname-pinned to the host helper, one backend (webapp / keycloak / server / grafana) — routing stays coarse (DD-242: the webapp's `/api`+`/otel` proxy is the tested data path, the gateway does not duplicate it). TLS backends (server, keycloak) get a `BackendTLSPolicy` pinned to the trust root (`global.trust.caSecretName` / the BYO `caBundle` Secret), plaintext backends (webapp) none. |
| CHT-31 | The umbrella generates `<release>-collector-legacy` with keys `token` (generate/preserve, the DD-254 pattern) and `otel-header` (composed `Bearer <token>`); its consumers so far: the webapp's nginx (`token`) and the Keycloak chart's rendered-but-dormant OTLP ref (`otel-header`, wired for real in 10.3b). |
| CHT-32 | Client-IP trust is declared twice, matching the two-hop edge (DD-261): the webapp's nginx gets a `realip` block from values (`nginx.trustedProxyCIDRs`, default empty — no hop trusted by default) resolving `X-Forwarded-For` before the `limit_req` geo bucket keys; the server's `FORWARDED_ALLOW_IPS` takes the webapp's network from environment values. The overlays name their clusters' pod CIDRs; a stock render trusts loopback only. |

## Deviations

From Java Atlas: none (platform slice). From the dev compose: the compose fronts the server with the webapp container-to-container (one hop, loopback trust by adjacency); in-cluster the Gateway is a real second hop and the trust chains are named instead of assumed (DD-261). The webapp's e2e resolves the nginx template with compose `configs:` (compose-time interpolation); in-cluster the same placeholders resolve at pod start (DD-262) — the compose stays the dev shape, the chart the deploy shape (the DD-253 sibling rule).

## Acceptance

- `npx nx run-many -t helm-lint helm-template` green — the five app charts now render workloads (the aux charts' test-values files finally boot-tested), and the umbrella renders Gateway + routes + edge cert.
- The chart-contract suite names every rule above; the nginx byte-copy has a drift guard (the DD-256 pattern); server/webapp uid pins assert the image's declared user (DD-257 pattern).
- Hand check (reported in the PR, scripted in 10.5): the full umbrella on minikube (all eight charts, Envoy Gateway installed per the runbook) reaches pod-Ready for every workload, the Gateway gets an external address through `minikube tunnel`, and a scripted request round-trips the tested data path: `https://atlas.atlas.test/api/atlas/admin/version` → gateway → webapp nginx `/api/` (TLS, `proxy_ssl_name` verified against the server's Certificate) → server → Elasticsearch answers; `keycloak.atlas.test/realms/master` answers through its route. No telemetry endpoint (10.3b).
- CI: `nx affected -t test e2e -c ci` green (the app e2e suites are unchanged compose-based; the new renders ride `helm-lint`/`helm-template` + the root suite).
