Deviations from Apache Atlas¶

Every behaviour of Aurelius Atlas that a client could observe and that differs from Apache Atlas 2.4.0 (ADR 046). The parity report links each tolerated difference to its entry here; a difference without an entry is a defect.

DV-04 is temporary

The most visible row in this table — "no endpoint needs a login" — is the current state of a planned sequence, not a security posture: authentication arrives with increment 6.1 and the deviation is removed then. Until 6.1, read every anonymous call in this repository as development-arrangement behaviour, not production design (ADR 039 names the boundary; ADR 046 keeps the shape Atlas clients expect when it lands).

# Area Apache Atlas behaviour Aurelius Atlas behaviour Reason Increment
DV-01 Notifications Publishes entity changes to Kafka; consumes hook messages Not supported Out of scope (ADR 050) 0.1
DV-02 Authorization Ranger or simple authorizer Simple authorizer only Out of scope; Ranger needs its own server 0.1
DV-03 Admin version names Apache Atlas 2.4.0 and its build revision Names Aurelius Atlas, its release and its revision A client must be able to tell which implementation answers 0.5
DV-04 Authentication Every endpoint except admin/status needs a login; the session reports the user, groups and permissions Until 6.1, no endpoint needs a login; the session reports no user, no groups and no entity permissions Authentication arrives in 6.1; removed then 0.5
DV-05 Admin The session's timezones are Java's TimeZone.getAvailableIDs() The IANA time zone ids of the server's tz database, sorted Java's list includes legacy three-letter ids the IANA database does not have 0.5
DV-06 Types A type definition's createdBy and updatedBy name the user who created and last updated it Until 6.1, absent There is no login until 6.1; removed then 1.4
DV-07 Types The built-in model types and the patch records name the operating system account the server runs as Name no user The account is an accident of deployment, and is the same for every type a process loads 1.5
DV-08 Types A patch without an id is recorded, without an id, at every start Is applied at every start and not recorded A record without an id cannot be found again; Atlas never matches it either 1.5
DV-09 Types /v2/types/typedefs and its headers list each kind in the hash order of the registry; of two notsupertype filters, the first in the request parameters' hash order applies Each kind sorted by name; the first notsupertype in the request applies Hash order is not something a client can rely on (DD-034) 1.6
DV-10 Types A write body that is not an AtlasTypesDef is answered by Jersey's JSON provider 400 BAD_REQUEST with Atlas's error body Atlas's source and tests do not state its answer 1.6
DV-11 Types A float attribute given a number beyond the double range fails with NumberFormatException, an internal error The value is invalid for float The failure is an unchecked exception in AtlasFloatType.isValidRange, not a decision; the type treats every other out-of-range value as invalid 2.1b
DV-12 Types A date value before year 1 or after year 9999 is valid The value is invalid for date Python's datetime holds years 1 to 9999; such dates do not occur in metadata 2.1b
DV-13 Types An entity type given a map without relationship attributes fails with NullPointerException, an internal error The map is checked as one without relationship attribute values The failure is an unchecked exception in AtlasEntityType.validateRelationshipAttributes, not a decision 2.1c
DV-14 Admin admin/patches lists the typedef patches and the Java patches that repair JanusGraph and Solr indexes Lists the typedef patches only The Java patches repair indexes Elasticsearch does not have 2.2
DV-15 Entities An entity's createdBy and updatedBy name the logged-in user Until 6.1, absent There is no login until 6.1 2.2
DV-16 Entities A request's entities are committed in one graph transaction, never seen half done A reader may see part of a multi-entity write while its bulk request runs; the outcome is all or nothing Elasticsearch has no multi-document transactions (ADR 047, DD-046) 2.2
DV-17 Entities A read by unique attributes given only a unique system attribute (attr:__guid) answers an arbitrary ACTIVE entity of the type Fails with INSTANCE_BY_UNIQUE_ATTRIBUTE_NOT_FOUND Atlas's lookup drops attributes the type does not hold as unique properties and then queries by type alone, an accident of findByUniqueAttributes 2.3
DV-19 Entities bulk/uniqueAttribute answers its entities in the hash order of the attr_<n> indices In the order the indices first appear in the query Java's order is that of a HashMap, which no client can rely on 2.3
DV-20 Entities A write that needs a unique value another entity holds fails with JanusGraph's SchemaViolationException, answered 500 with a plain-text logged id 500 INTERNAL_ERROR with Atlas's error body naming the value and its holder; also for a write that loses two races The plain-text answer hides the cause; a race is retried once (DD-052) 2.4
DV-21 Entities The references of an array, and an array's relationships, are ordered by the hash order of their edges; entities a new reference made updated are reported in a HashMap's order Kept in the request's order, after the relationships that stay; reported in the order reached Hash order is not something a client can rely on 2.4
DV-23 Entities A partial update appending (isAppendOnPartialUpdate) to a stored array or map of references fails with INVALID_OBJECT_ID Appends Atlas maps the stored edges as if they were request values; appending is what the option asks for 2.4
DV-24 Entities A POST without a body, or a bulk write without entities, fails with a NullPointerException, an internal error INVALID_PARAMETERS, as for a null entity or an empty list The failure is an unchecked exception in AtlasEntityStream, not a decision 2.4
DV-25 Entities Deleted and changed entities of a delete are listed in the hash order of the request context's maps In the order they were reached Hash order is not something a client can rely on 2.5
DV-26 Entities Deleting an entity a mandatory reference names fails with a message naming the referring vertex and its graph details Names the referring entity's GUID Aurelius Atlas has no vertices 2.5
DV-27 Entities Every entity referring to a deleted one is changed in the same graph transaction Referring entities are found by a search, which may miss one written at the same moment as the delete Elasticsearch has no incoming edges (DD-057) 2.5
DV-28 Relationships A relationship without end1 or end2 fails with a NullPointerException, an internal error RELATIONSHIP_END_IS_NULL The failure is an unchecked exception, not a decision 3.1
DV-29 Relationships An update without propagateTags fails with a NullPointerException Keeps the stored propagateTags The failure is an unchecked exception in updateTagPropagations, not a decision 3.1
DV-30 Relationships Relationships to one entity are created without touching it Both ends' documents list the relationship, so concurrent writers relating many entities to one retry more often Entity reads stay gets by id (DD-061) 3.1
DV-32 Relationships An inverseRef whose inverse attribute is no relationship attribute is kept as a legacy edge Not maintained Plain references are attribute values (DD-049), and Atlas types since 1.0 use relationships instead 3.1
DV-33 Entities A reference an update drops from an array or map of plain references stays, its edge soft-deleted, and reads back after a soft delete Dropped A plain reference keeps no state of its own (DD-049, DD-058) 2.4
DV-35 Classifications An entity create with a classification of an unknown type fails with a NullPointerException, an internal error CLASSIFICATION_NOT_FOUND The failure is an unchecked exception, not a decision 3.3
DV-36 Classifications bulk/setClassifications with a header without attributes, a type without unique attributes, or no body fails with a NullPointerException or NoSuchElementException The header is skipped as not found, <no unique name> named; no body answers [] The failures are unchecked exceptions, not decisions 3.3
DV-38 Classifications Tasks run one at a time on the active instance, in creation order Every server process runs tasks, each claimed by one, so tasks may run side by side Several processes share the store without a leader (DD-080) 3.4
DV-39 Audit A count, offset or auditAction of {guid}/audit that is not one fails with Jersey's parameter error, answered as a 500 with a text body It fails with BAD_REQUEST A malformed parameter is the client's error; Atlas's answer is its generic mapper, not a decision 3.5
DV-40 Audit Audit events are written in the request before the graph commits; a failed commit leaves events of a change not made Events are written after the change committed; a process stopping in between loses them The audit has its own index, written from the committed entities (DD-082) 3.5
DV-41 Audit A tagUpdateStartTime of bulk/headers that is not a number fails with Jersey's parameter error, answered as a 500 with a text body It fails with BAD_REQUEST A malformed parameter is the client's error, as DV-39 3.5
DV-42 Audit Classification add and update events write the request's classification object, normalised They write the instance as a read answers it Events are recorded after the write, from what is stored (DD-085) 3.5
DV-43 Search LIKE is its in-memory contains and, besides, a pattern of the index or graph query LIKE is contains alone The search is one query (DD-089); the in-memory predicate is the one Atlas applies in every case 4.1
DV-44 Search Named TIME_RANGEs are computed in the server's time zone They are computed in UTC A server's zone should not change what a search finds 4.1
DV-45 Search A marker encodes the hash Java computes of the search parameters It encodes a hash of Aurelius Atlas's own; Atlas's markers are invalid here Java's hashCode is not reproduced 4.1
DV-46 Search classification, query, termName are searched; no parameters or a filter value of another type fail with Java exceptions Until 4.1b, 4.2, 5.2 these fail with BAD_REQUEST; no parameters is INVALID_SEARCH_PARAMS Refusing beats a wrong answer; Java's exceptions are not decisions 4.1
DV-47 Search A wildcard classification name is a regular expression over the entity's pipe-separated names; its * spans names Each name is matched on its own A pattern names one classification 4.1
DV-48 Search A free-text query is read by Solr's edismax: AND, OR, NOT in either case, field:value It is read as simple_query_string: +, \|, - and quotes A malformed query must not fail the search (DD-092) 4.2
DV-49 Search With free text enabled, fulltext searches __fullText, which is no longer written, and finds nothing new fulltext answers from the free text An endpoint that finds nothing helps no client 4.2
DV-64 Interface Serves its own dashboards: dashboardv2 at / and dashboardv3 at /n/ Serves the Aurelius webapp, a web interface of its own design (ADR 053) The product interface is Aurelius's own; the Atlas dashboards stay as the parity reference 7.10
DV-65 Interface No settings control: per-user UI preferences live in the dashboard's UserSettings store, not the header A settings panel (theme, language, time zone, page size, telemetry) opens from the header gear The panel is Aurelius's own interface (ADR 053), stores per browser (DD-161), and touches no Atlas endpoint 7.14
DV-66 Interface No alerts surface: feature toasts, Kafka hook messages to clients An alerts drawer collects app-level alerts (runtime and HTTP errors) The drawer is Aurelius's own interface (ADR 053), touches no Atlas endpoint 7.15
DV-67 Auxiliary API No entity-validation endpoint (the legacy Aurelius app calls a validation service that is itself a mock: it accepts any entity) aurelius-atlas-validate-entity ships the legacy mock contract verbatim, with the workspace's auth and observability The legacy backend is a mock (ADR 055); the browser contract is kept, real validation is a future server rule 8.3
DV-68 Auxiliary API No model-extraction endpoint (the legacy Aurelius app draws lineage via data2model, whose ar3 model comes from the m4i-analytics library: pandas, graphviz, bokeh) aurelius-atlas-data2model reimplements the ar3 output natively; coordinates are deterministic LR-layout numbers, not graphviz positions The browser contract ({model, metadata}) is kept; the legacy library's tree is a retired product's dependency (ADR 055) 8.1
DV-69 Auxiliary API No lineage-flattening endpoint (the legacy Aurelius app flattens Atlas m4i_*_process lineage via lineage_model against its own Atlas) aurelius-atlas-lineage-model reads a configurable Atlas base URL; 8.2 fixtures stand in until the server's lineage feed (5.1) wires it The API ships before its data path so no increment blocks on 5.1 (ADR 055); one upstream setting, no hardcoded host 8.2
DV-70 Auxiliary API data2model renders a null element name as the string 'nan' (pandas' %s of a NaN cell) A null element name yields '' The 'nan' string is a pandas artefact, not a contract; the JSON body carries null as null (DD-198, DTM-02) 8.1
DV-71 Auxiliary API data2model returns its JSON answer as text/html (Flask's dumps and default content type) The answer is application/json; the body contract is unchanged The content type is a Flask accident; the body is the contract (DTM-01) 8.1
DV-72 Auxiliary API lineage_model crashes on an invalid depth/direction query parameter — int()/Enum() raise, Flask answers 500 An invalid query parameter is 400 BAD REQUEST with Atlas's error body Input the request model rejects at the boundary is a client error, not a server fault (LM-07, DD-197 apps) 8.2
DV-73 Auxiliary API lineage_model without a guid fetches the literal guid None (upstream 404, answered 204) A missing guid is 400 BAD REQUEST with Atlas's error body The literal-None fetch is a Flask params.get accident; a required parameter is required (LM-07) 8.2
DV-74 Auxiliary API lineage_model accepts any syntactically present bearer token — @requires_auth(transparent=True) forwards it unvalidated GET / verifies the token for this app's audience (AUX-05) before forwarding it; browser tokens (azp aurelius) pass unchanged An unvalidated pass-through lets a forged token reach Atlas/data2model with the caller's identity; every 8.x app validates its own audience (DD-197); forwarding the raw token is unchanged (LM-08) 8.2
DV-75 Auxiliary API validate_entity accepts any syntactically present bearer token — @requires_auth(transparent=True), and the mock never reads the token POST / verifies the token for this app's audience (AUX-05); nothing is forwarded — the app has no upstreams DV-74's pattern (DD-197): an unvalidated pass-through is pointless on an app with no upstreams, and a forged token gains nothing; browser tokens (azp aurelius) pass unchanged (VE-03) 8.3
DV-76 Auxiliary API The legacy's healthcheck is m4i_backend_core's GET /heartbeat → 200 {"success": true} The healthcheck is GET /liveness → 204, empty body One route, status, and empty body across the 8.x apps' container healthchecks (DD-197 family); no caller reads /heartbeat's body (VE-04) 8.3
DV-77 Auxiliary API lineage_model calls its upstreams bare (requests.post, m4i-atlas-core.get_lineage_by_guid) — every request pays a full timeout while an upstream is down Each upstream is guarded by a circuit breaker (pybreaker, the auth library's convention, AUX-02): outages (5xx, transport) open the circuit, the open circuit answers 502 fast without calling, and a half-open trial closes it The legacy has no resilience device; fast-fail protects the pool and the caller, and the 502 is DV-80's existing wire shape (LM-11..LM-14) 8.5
DV-78 Auxiliary API lineage_model treats the guid as an opaque string — any token is fetched from upstream verbatim (a malformed guid costs a round trip) The lineage chain types the guid as UUID end to end (route query, client models/methods, LineageInfo keys and headers, relation endpoints); a non-UUID guid is DV-73's 400 before any upstream call; relationshipId stays str Atlas guids are UUIDs (Entity.getGuidAsString), so the type is the wire's own shape; pydantic/httpx keep the JSON bytes canonical (format: uuid, lowercase strings) and the extract engine stringifies the rows (LM-01, LM-07, CL-11, CL-12, CL-30) 8.5
DV-79 Auxiliary API data2model answers a malformed extraction body with a Flask ValueError — a 500 A malformed body is 400 BAD_REQUEST with Atlas's error body Input the request model rejects at the boundary is a client error, not a server fault (DTM-11) 8.1
DV-80 Auxiliary API lineage_model lets upstream failures escape — a lineage 5xx, a relation naming a guid absent from guidEntityMap (KeyError), a failing /extract (raise_for_status) all reach Flask as 500 An upstream failure is 502 BAD GATEWAY with Atlas's error body; the caller's token is never leaked into the message A dependency that fails is a gateway condition, and a 500 from uncaught internals is an accident (LM-07) 8.2
