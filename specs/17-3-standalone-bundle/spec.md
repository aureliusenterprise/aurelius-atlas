## Scope

A person outside the repository cannot run the standalone stack today. The stack is a tree of compose files
that reach into `apps/` and `infra/`, the images it names carry `:local`, and a fresh clone must run
`nx certgen` before the stack starts. This increment turns that tree into one delivery artifact: a bundle the
release job publishes, which a person unpacks on their own machine and starts with two commands.

It delivers:

- A bundle, generated by one target at release or packaging time and never committed. The target resolves the
  stack and copies the assets it mounts into one folder (SBD-01).
- One compose file, produced by `docker compose` itself. It holds the whole stack with no `include` or
  `extends` left to read, and it keeps every `${VAR}` the pieces wrote, so a setting is changed in one place
  (SBD-02, DD-689). The relative paths of the repository become paths inside the bundle (SBD-03, DD-690).
- The sample folder inside the bundle, and no secrets. Every secret is a value the person fills in the
  bundle's one `.env` file, and the `.env.example` of 17.2 is that file's starting point (SBD-04, SBD-05).
- Image references the stack can re-point. Every piece names its own image through a compose variable
  (SBD-11), and the bundle sets those variables to the release's images, so it names no `:local` tag
  (SBD-06).
- One script that builds the bundle, and one check the repository runs on every pull request. The check
  builds a bundle from the working tree and starts it against a real Docker daemon (SBD-07, SBD-08).

It does not deliver, with the increment that will:

| Not delivered                                                                                                                          | Lands with              |
| -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| Production hardening of the stack's settings (restart policy, resource caps, image digest pinning, container hardening, exposed ports) | the hardening increment |
| A signed bundle (cosign or an OCI artifact attestation over the archive itself)                                                        | the hardening increment |
| An installer, a GUI, or a single host machine image                                                                                    | not planned             |

## Semantics

"The standalone stack" is the compose system in `docker/` that serves the webapp, the server with its
dashboards, the store, the identity provider, and the telemetry (ADR 065). "A piece" is one compose file the
umbrella includes or extends. An "asset" is a file a piece mounts into a container: a configuration file, a
theme folder, a certificate folder, or a script. "A bundle" is one folder tree, shipped as one archive, that
contains every piece and asset the standalone stack needs. "A closed bundle" is a bundle that references
nothing outside itself. The "release tag" is the image tag the release job publishes for a version, such as
`0.1.0-rc.9`. The "image variables" are the six compose variables named `<PROJECT>_IMAGE` that name the
stack's own images.

| SBD-01 | The bundle is a generated artifact. One repository target creates it, from the tree it builds in, and nothing in the bundle is a committed file. `git status` is clean after the target runs (DD-682).                                                                                                                                                                                                                                                                                                  |
| SBD-02 | The bundle ships one compose file: the stack resolved by `docker compose config --no-interpolate`. | SBD-03 | A closed bundle names no path outside itself. Every host path the flat file names resolves inside the bundle: the target copies each mounted file or folder and rebases each path to the bundle. A guarded folder stays a variable, and the bundle's `.env` answers it. A path the target cannot copy or resolve fails the target (DD-690).                                                                                                                                                             |
| SBD-04 | The bundle carries no secret value. It ships the settings roster of increment 17.2's `.env.example` as its own `.env`, with every secret named and left empty, and it holds no private key, no certificate, no truststore, and no filled secret (DD-684). A certificate the stack needs at start-up is either made by the bundle's own script or supplied by the person (SBD-09).                                                                                                                       |
| SBD-05 | The bundle ships the sample folder. The server piece requires `SAMPLE_DIR` and the bundle's `.env` names it, so the sample import and the tenants one shot read the sample while the person sets no folder. The person can point `SAMPLE_DIR` at their own folder (DD-684, DD-687).                                                                                                                                                                                                                     |
| SBD-06 | The bundle sets all six image variables to the release tag of the build that produced it, so its services name no `:local` tag. The compose copies keep the variables with their `:local` default and are otherwise unchanged (DD-685). A bundle built without a release version fails the check (DD-685).                                                                                                                                                                                              |
| SBD-07 | The repository holds one bundling implementation, in the repository's own scripting language and covered by tests. It reads the stack's own compose files and copies what they reference. It keeps no second copy of a service definition, a mount list, or an image name (DD-682).                                                                                                                                                                                                                     |
| SBD-08 | The repository's standalone suite builds a bundle from the working tree and checks it with no Docker daemon: it is closed (SBD-03), free of secrets (SBD-04), resolved with its own `.env` free of `:local` tags (SBD-06), and its service, image, and volume names equal the repository stack's. A level 2 run starts the bundle on a real Docker daemon and opens the webapp through the proxy (SBD-08).                                                                                              |
| SBD-09 | The bundle starts a working stack on a machine that holds no repository and no developer tooling. `bash make-certs.sh` makes the certificates, the person fills the empty secrets in the bundle's `.env`, and one `docker compose up -d` starts the stack. The person needs Docker Engine, `docker compose`, `bash`, and `openssl` only (SPS-09 carried the script).                                                                                                                                    |
| SBD-10 | The repository's own stack keeps working unchanged. The e2e stacks keep extending the app pieces in place, `nx serve` keeps the `:local` images and the repository paths, and no repository compose file changes its service definitions for the bundle's sake (DD-682).                                                                                                                                                                                                                                |
| SBD-11 | Every piece of the stack names the image it runs through its own image variable, with the `:local` tag as the default. No piece names an Aurelius image in plain text. A one shot that runs another project's image names that project's variable (DD-686).                                                                                                                                                                                                                                             |
| SBD-12 | No app piece names a certificate or sample folder with a default path. Each names its folder through a required variable, so an install that sets no folder fails the start with the variable's name instead of reading a path of the repository. The bundle keeps each such mount as that variable, typed `bind`, and answers it in its `.env`. The three infra pieces keep their own literal paths, and the flat file keeps them pointing at the same folder name inside the bundle (DD-687, DD-690). |

## Java origin

None. This increment ports no Apache Atlas behaviour. It packages one Aurelius deployment for delivery

## Deviations

None new. This increment moves no Apache Atlas behaviour and changes no REST rule. It packages the
standalone stack that ADR 065 and ADR 066 place, and that stack's difference from Apache Atlas's own
single-container demo stays where it is recorded today.

## Acceptance

- `uv run pytest tests/test__standalone_bundle.py` (no Docker daemon): the bundler's tests, one per rule id
  `SBD-01` to `SBD-08`, each named with `@pytest.mark.covers(..., rules=["SBD-NN"])`. They build a bundle
  from the tree into a temporary folder and assert closure, secret-freedom, image tags, and service-set
  equality against the repository stack the conftest resolver already flattens (`standalone_compose`).
- `uv run pytest tests/test__standalone_host.py` stays green (17.2's rules do not move) and the rest of the
  root suite stays green.
- Level 2, recorded in the pull request: build a bundle with the target, unpack it in an empty folder, run
  `make-certs.sh`, fill `.env`, `docker compose up -d`, and open `https://localhost:9000/` and the sign-in
  page through the proxy. The command list goes in the bundle README (`README.md`, Start) and in the PR note.
- Docs gates: prettier, `zensical build --strict`, markdownlint on the changed files.
