# Deviations from Apache Atlas

Every behaviour of Aurelius Atlas that a client could observe and that differs from Apache Atlas 2.4.0 ([ADR 046](<https://aureliusenterprise.github.io/feat-aux-apis-lineage-model/architecture/adr/046-the-catalogue-keeps-its-public-contract/index.md>)). The parity report links each tolerated difference to its entry here; a difference without an entry is a defect.

> [!NOTE]
>
> **DV-04 is temporary**
>
> The most visible row in this table — "no endpoint needs a login" — is the current state of a planned sequence, not a security posture: authentication arrives with increment 6.1 and the deviation is removed then. Until 6.1, read every anonymous call in this repository as development-arrangement behaviour, not production design ([ADR 039](<https://aureliusenterprise.github.io/feat-aux-apis-lineage-model/architecture/adr/039-data-is-protected-where-it-travels-and-where-it-rests/index.md>) names the boundary; [ADR 046](<https://aureliusenterprise.github.io/feat-aux-apis-lineage-model/architecture/adr/046-the-catalogue-keeps-its-public-contract/index.md>) keeps the shape Atlas clients expect when it lands).

| \# | Area | Apache Atlas behaviour | Aurelius Atlas behaviour | Reason | Increment |
| --- | --- | --- | --- | --- | --- |
| DV-01 | Notifications | Publishes entity changes to Kafka; consumes hook messages | Not supported | Out of scope ([ADR 050](<https://aureliusenterprise.github.io/feat-aux-apis-lineage-model/architecture/adr/050-the-system-carries-only-what-the-catalogue-needs/index.md>)) | 0.1 |
| DV-02 | Authorization | Ranger or simple authorizer | Simple authorizer only | Out of scope; Ranger needs its own server | 0.1 |
| DV-03 | Admin | `version` names Apache Atlas 2.4.0 and its build revision | Names Aurelius Atlas, its release and its revision | A client must be able to tell which implementation answers | 0.5 |
| DV-04 | Authentication | Every endpoint except `admin/status` needs a login; the session reports the user, groups and permissions | Until 6.1, no endpoint needs a login; the session reports no user, no groups and no entity permissions | Authentication arrives in 6.1; removed then | 0.5 |
| DV-05 | Admin | The session's `timezones` are Java's `TimeZone.getAvailableIDs()` | The IANA time zone ids of the server's tz database, sorted | Java's list includes legacy three-letter ids the IANA database does not have | 0.5 |
| DV-06 | Types | A type definition's `createdBy` and `updatedBy` name the user who created and last updated it | Until 6.1, absent | There is no login until 6.1; removed then | 1.4 |
| DV-07 | Types | The built-in model types and the patch records name the operating system account the server runs as | Name no user | The account is an accident of deployment, and is the same for every type a process loads | 1.5 |
| DV-08 | Types | A patch without an id is recorded, without an id, at every start | Is applied at every start and not recorded | A record without an id cannot be found again; Atlas never matches it either | 1.5 |
| DV-09 | Types | `/v2/types/typedefs` and its headers list each kind in the hash order of the registry; of two `notsupertype` filters, the first in the request parameters' hash order applies | Each kind sorted by name; the first `notsupertype` in the request applies | Hash order is not something a client can rely on (DD-034) | 1.6 |
| DV-10 | Types | A write body that is not an `AtlasTypesDef` is answered by Jersey's JSON provider | `400 BAD_REQUEST` with Atlas's error body | Atlas's source and tests do not state its answer | 1.6 |
| DV-11 | Interface | Serves its own dashboards: `dashboardv2` at `/` and `dashboardv3` at `/n/` | Serves the Aurelius webapp, a web interface of its own design (ADR 053) | The product interface is Aurelius's own; the Atlas dashboards stay as the parity reference | 7.10 |
| DV-12 | Interface | No settings control: per-user UI preferences live in the dashboard's `UserSettings` store, not the header | A settings panel (theme, language, time zone, page size, telemetry) opens from the header gear | The panel is Aurelius's own interface (ADR 053), stores per browser (DD-073), and touches no Atlas endpoint | 7.14 |
| DV-13 | Interface | No alerts surface: feature toasts, Kafka hook messages to clients | An alerts drawer collects app-level alerts (runtime and HTTP errors) | The drawer is Aurelius's own interface (ADR 053), touches no Atlas endpoint | 7.15 |
| DV-14 | Auxiliary API | No entity-validation endpoint (the legacy Aurelius app calls a validation service that is itself a mock: it accepts any entity) | `aurelius-atlas-validate-entity` ships the legacy mock contract verbatim, with the workspace's auth and observability | The legacy backend is a mock (ADR 055); the browser contract is kept, real validation is a future server rule | 8.3 |
| DV-15 | Auxiliary API | No model-extraction endpoint (the legacy Aurelius app draws lineage via `data2model`, whose ar3 model comes from the `m4i-analytics` library: pandas, graphviz, bokeh) | `aurelius-atlas-data2model` reimplements the ar3 output natively; coordinates are deterministic LR-layout numbers, not graphviz positions | The browser contract (`{model, metadata}`) is kept; the legacy library's tree is a retired product's dependency (ADR 055) | 8.1 |
| DV-16 | Auxiliary API | No lineage-flattening endpoint (the legacy Aurelius app flattens Atlas `m4i_*_process` lineage via `lineage_model` against its own Atlas) | `aurelius-atlas-lineage-model` reads a configurable Atlas base URL; 8.2 fixtures stand in until the server's lineage feed (5.1) wires it | The API ships before its data path so no increment blocks on 5.1 (ADR 055); one upstream setting, no hardcoded host | 8.2 |
| DV-17 | Auxiliary API | `data2model` renders a null element name as the string `'nan'` (pandas' `%s` of a NaN cell) | A null element name yields `''` | The `'nan'` string is a pandas artefact, not a contract; the JSON body carries null as `null` (DD-109, DTM-02) | 8.1 |
| DV-18 | Auxiliary API | `data2model` answers a malformed extraction body with a Flask `ValueError` — a 500 | A malformed body is `400 BAD_REQUEST` with Atlas's error body | Input the request model rejects at the boundary is a client error, not a server fault (DTM-11) | 8.1 |
| DV-19 | Auxiliary API | `data2model` returns its JSON answer as `text/html` (Flask's `dumps` and default content type) | The answer is `application/json`; the body contract is unchanged | The content type is a Flask accident; the body is the contract (DTM-01) | 8.1 |
| DV-20 | Auxiliary API | `lineage_model` crashes on an invalid `depth`/`direction` query parameter — `int()`/`Enum()` raise, Flask answers 500 | An invalid query parameter is `400 BAD REQUEST` with Atlas's error body | Input the request model rejects at the boundary is a client error, not a server fault (LM-07, DD-108 apps) | 8.2 |
| DV-21 | Auxiliary API | `lineage_model` without a `guid` fetches the literal guid `None` (upstream 404, answered 204) | A missing `guid` is `400 BAD REQUEST` with Atlas's error body | The literal-`None` fetch is a Flask `params.get` accident; a required parameter is required (LM-07) | 8.2 |
| DV-22 | Auxiliary API | `lineage_model` lets upstream failures escape — a lineage 5xx, a relation naming a guid absent from `guidEntityMap` (`KeyError`), a failing `/extract` (`raise_for_status`) all reach Flask as 500 | An upstream failure is `502 BAD GATEWAY` with Atlas's error body; the caller's token is never leaked into the message | A dependency that fails is a gateway condition, and a 500 from uncaught internals is an accident (LM-07) | 8.2 |
| DV-23 | Auxiliary API | `lineage_model` accepts any syntactically present bearer token — `@requires_auth(transparent=True)` forwards it unvalidated | `GET /` verifies the token for this app's audience (AUX-05) before forwarding it; browser tokens (azp `aurelius`) pass unchanged | An unvalidated pass-through lets a forged token reach Atlas/data2model with the caller's identity; every 8.x app validates its own audience (DD-108); forwarding the raw token is unchanged (LM-08) | 8.2 |
